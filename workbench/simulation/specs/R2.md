# R2 — Authorization, scope and execution binding
Status: targeted research completed; U2 specification prepared before execution.
Evidence: OWASP distinguishes authentication from authorization, requires deny-by-default access and permission checks on every request [web:90]. Its transaction guidance calls for server-side checks and a final authorization control tied to execution, including changed data and TOCTOU concerns [web:89]. OWASP secure AI coding guidance adds task-scoped tool access, MCP definition review, resource limits and caution around auto-accept [web:91].
Applied distinction: review HOLD is a workflow status; no protected execution occurs under HOLD. DENY is an access decision, not a judgment about a person's moral worth. ALLOW_SCOPED in reference tests permits only a hypothetical fixture action.
Design change after U1: model review separately from action binding; require exact actor/action/resource/arguments/version/revision, expiry, current permission, unrevoked authority and a single-use identifier. An approval digest is not a cryptographic signature or proof of identity; store approval records behind a trusted service boundary.
Challenge: exhaustive testing is exhaustive only over the finite declared input domain. A program agreeing with an authored oracle does not establish moral completeness or independent scientific validation. In-memory consumed identifiers do not establish concurrent replay protection; atomic persistence is a separate U3 topic.
