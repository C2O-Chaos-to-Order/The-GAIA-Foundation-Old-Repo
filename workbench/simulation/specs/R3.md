# R3 — Persistence, failure recovery and artifact reproducibility
Status: targeted research completed before U3 execution.
Evidence: SQLite defines atomic transactions as all changes occurring or none, and describes rollback recovery and hardware/filesystem assumptions [web:104]. The inspected atomic-commit article specifically explains rollback mode; do not claim it describes the WAL implementation. The backup API provides consistent database snapshots with explicit completion/error handling [web:102]. ACM encourages preserved software/data artifacts and review procedures supporting reruns; its policy terminology has evolved, so this release avoids assigning itself an artifact badge [web:120].
Method change after U2: persist stable IDs and evidence statuses; exercise actual file-backed SQLite with foreign keys and transactions, controlled two-connection lock interleaving, version conflict, close/reopen, backup, unknown-outcome reconciliation and public-only archive roundtrip.
Critical distinction: database atomicity does not make an external email, tool write, robot action or OS action exactly once. The experiment includes no external effects. Intent recovery must not guess success and must not retry an uncertain non-idempotent action automatically.
Challenge: no power-cut testing, kill-process crash injection, disk-full fault, encryption, hostile OS administrator, concurrent load, or browser/HTTP application tests. Public fixture filtering is not a complete privacy assurance. Independent team review remains absent.
